# Benchmark

`@null-city/benchmark` plays NullCity end to end with deterministic,
non-LLM policies through the same public `PlayerSession` contract as the
browser and MCP adapter (`docs/protocol.md`). This document explains how to
run it, what each report field means, and how to independently recompute
any number in a report. See `packages/benchmark/README.md` for the
package-level API/test reference; this file is the outside-in "why/how to
read a report" version.

## Why a benchmark, and what it is not

NullCity's product thesis (`00_NORTH_STAR.md`) is that acting under
uncertainty — delayed, incomplete, sometimes false information — is a
harder and more realistic test than acting on directly-readable state. The
benchmark exists to make that comparison quantitative and reproducible:
same scenario, same seed, different policy, materially different outcome.

It is **not** an LLM leaderboard. The three shipped baselines are pure,
non-LLM functions of `PlayerSessionState`; an LLM-backed policy is possible
(see `packages/mcp-server/examples/llm-openai-policy.mjs`) but is explicitly
outside `pnpm verify`/`pnpm test`/CI, since a default gate that requires a
paid API key is not reproducible by every contributor.

## Running it

```bash
pnpm build
pnpm bench                       # full default matrix: all scenarios x seeds x policies
node packages/benchmark/dist/cli.js --scenario black-river --seed 49314 --policy verification-first --out data/benchmark
```

`pnpm verify:benchmark` runs a fixed, fast slice (all 3 scenarios × all 3
policies × 1 seed, `--tick-step 30`) as one of the required `pnpm verify`
gates — no API key, completes in a few seconds.

See `packages/benchmark/README.md` for the full CLI flag reference.

## Baselines

| Policy | Behavior |
|---|---|
| `noop` | Never issues a command or assessment. The floor every other policy should beat. |
| `reactive-greedy` | Dispatches every idle, non-verification team to the oldest unresolved claim in a district no other team is already headed to. No belief tracking. |
| `verification-first` | Prioritizes verification teams at the oldest contested/reported claim; submits one deterministic prior probability per claim on first observation; otherwise dispatches like `reactive-greedy`. |

## Metrics (recomputable from the public event log alone)

Every `PublicScoreChanged` event on the public stream echoes the exact
score-category id and delta that `packages/simulation/src/score.ts#computeScore`
computed internally (`docs/scoring.md`), so `computeMetrics()`
(`packages/benchmark/src/metrics.ts`) — and anyone re-reading the same log —
can sum a category's deltas and get its exact contribution to the final
score, without ever needing truth-side values:

| Field | Meaning |
|---|---|
| `scoreTotal`, `finalTick`, `phase` | Terminal outcome. |
| `populationRiskScoreContribution`, `infrastructureScoreContribution` | Sum of `PublicScoreChanged.delta` for those categories. |
| `responseLatencies`, `meanResponseLatencyTicks` | Per claim: ticks between first observation and the first accepted command targeting its district at/after that tick. |
| `invalidCommandCount`, `invalidCommandRate`, `commandsByName` | Fraction of rejected `CommandResult` events. |
| `resourceEfficiencyScore`, `wastedDispatchPenalty` | Sum of the matching score-category deltas. |
| `falseAdvisoryCost` | Sum of `misadvisory` category deltas. |
| `cascadeCount`, `cascadePenalty` | Count/delta-sum of `chain_failure` category events. |
| `brierScore`, `calibrationBins` | Mean squared error of each resolved claim's latest pre-resolution probability vs. its verified/refuted outcome; 10 probability-decile bins. |
| `verificationInfoGain` | Mean squared-error reduction after `VerificationResolved`, across claims with assessments on both sides. Positive means verification measurably improved beliefs. |

## Reading a report

`report.json` (`{ format: "nullcity-benchmark-report", version: 1, runs: RunRecord[] }`)
is the machine-readable source of truth; `report.md` is a human-readable
render of the same `RunRecord[]` — every cell traces back to a field above,
nothing is computed only for display.

## Real excerpt from this candidate

The table below is copied verbatim from `data/benchmark-smoke/report.md`,
generated by `pnpm verify:benchmark` against this exact codebase (see
`EVIDENCE.md` for the command, exit code, and full per-run detail).
Re-generate it yourself with `pnpm verify:benchmark`.

| Scenario | Seed | Policy | Verified | Final Tick | Score | Cascades |
|---|---|---|---|---|---|---|
| black-river | 49314 | noop | yes | 540 | -95.10 | 2 |
| black-river | 49314 | reactive-greedy | yes | 540 | -43.61 | 2 |
| black-river | 49314 | verification-first | yes | 540 | -44.76 | 2 |
| glass-harbor | 49314 | noop | yes | 480 | -68.23 | 2 |
| glass-harbor | 49314 | reactive-greedy | yes | 480 | -30.66 | 2 |
| glass-harbor | 49314 | verification-first | yes | 480 | **14.51** | 2 |
| signal-zero | 49314 | noop | yes | 450 | -59.42 | 1 |
| signal-zero | 49314 | reactive-greedy | yes | 450 | -55.43 | 1 |
| signal-zero | 49314 | verification-first | yes | 450 | -35.16 | 1 |

Every active policy beats `noop` across the five shipped scenarios
(`black-river`, `glass-harbor`, `signal-zero`, `mirror-district`,
`red-ledger`). The excerpt below focuses on the original three; the full
matrix is regenerated by `pnpm verify:benchmark` into
`data/benchmark-smoke/report.md`. `verification-first`
beats `reactive-greedy` by **+45.17** on Glass Harbor (debunking a false
attribution before dispatching is decisive there) and by **+20.27** on
Signal Zero (prioritizing verification against spoofed telemetry pays off),
but is marginally *worse* than `reactive-greedy` on Black River (−44.76 vs.
−43.61 — reacting fast to the power/water cascade matters more than
verification there). This is the "meaningfully different baseline
behavior per scenario" claim, and it is an executable regression gate, not
just a report reading — see `packages/benchmark/test/distinctness.test.ts`.

## Provenance and model metadata

`RunRecord` carries whatever policy/model metadata a policy chooses to
attach (empty for the three built-in deterministic baselines). An LLM
adapter is expected to record provider/model/configuration on its `RunRecord`
so a report never presents a model-backed run as if it were a
deterministic baseline.
