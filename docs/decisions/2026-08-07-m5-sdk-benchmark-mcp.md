# ADR — M5 SDK, Benchmark, and MCP Adapter

## Status

Implemented for M5, awaiting owner acceptance.

## Decision

1. **`@null-city/sdk` (`packages/sdk`) is a runtime-validated, retrying wrapper over the public REST/WS surface only — never an in-process shortcut.** `createPlayerSession` (`src/session.ts`) returns a `PlayerSession` (`src/types.ts`) whose every method delegates to `RestTransport` (`src/rest.ts`), which parses every response through a zod schema (`src/schemas.ts`) before any field reaches caller code, and never talks to `@null-city/simulation`/`@null-city/epistemics` even in its own tests (only as **dev**-only dependencies, used solely for test fixtures/leak-scanning). Retryability is decided per call, not per SDK: `getState`/`getEvents`/`getCompletedRun` are pure reads and always retried on transient failure; `submitCommand` is retried against its `idempotencyKey` (auto-generated with `crypto.randomUUID()` when omitted) — the engine rejects a re-submitted key with `duplicate_command` rather than re-executing it, surfaced as `outcome.deduplicated === true`, never as a fresh rejection; `advance` and `submitAssessment` have no server-side dedup key (a duplicate would double-advance the clock or double-record a belief), so the SDK never auto-retries them and a network failure surfaces immediately as a `NetworkError`.
2. **`@null-city/benchmark` (`packages/benchmark`) plays the exact same `PlayerSession` a human or an LLM would, over a real loopback HTTP server it owns for the run's lifetime — not an in-process shortcut either.** `runOne` (`src/runner.ts`) spins an ephemeral `@null-city/server`, drives a `Policy` (`src/policy.ts`) — a pure `(PlayerSessionState) -> {commands, assessments}` function — through a decide/act/advance loop with a hard per-decision output cap (`MAX_COMMANDS_PER_DECISION`/`MAX_ASSESSMENTS_PER_DECISION` = 10) and a wall-clock timeout per `policy.decide()` call (`withTimeout`, default 250ms) so a slow or runaway policy degrades to a recorded error/truncation rather than hanging or flooding the transport. The three shipped policies (`noop`, `reactive-greedy`, `verification-first`; `src/policies/`) are deterministic, non-LLM, and require no API key, satisfying "no API key required for default suite" directly. `runMatrix` (`src/matrix.ts`) sweeps `(scenarioId, seed, policyId)` combinations; `src/report.ts` writes both a JSON artifact (`{format, version, runs: RunRecord[]}`, one record per run with the full command/assessment/error log, `playerLogHash`, and `metrics`) and a human-readable Markdown comparison, every cell of which traces back to a `RunRecord` field.
3. **Every benchmark metric (`src/metrics.ts#computeMetrics`) is a pure function of the run's already-verified public player event stream, not truth.** `runOne` calls `verifyPlayerEventStream` before `computeMetrics` ever sees the log, so a tampered or non-hash-chained log is never scored. Score-category metrics (population risk, infrastructure, cascade count/penalty, wasted dispatch, false-advisory cost, resource efficiency) sum `PublicScoreChanged.delta` by `category` — these category `id`s are exactly what `packages/simulation/src/score.ts#computeScore` emits and `packages/epistemics/src/bridge.ts` echoes verbatim onto the public stream, so summing them reproduces each category's exact score contribution without the metrics module ever touching a truth percentage. Response latency is ticks between a claim's first observation and the first accepted command targeting its district; invalid command rate is the fraction of `CommandResult(rejected)`; Brier score/calibration bins compare each resolved claim's latest pre-resolution assessed probability against its `verified`/`refuted` outcome; verification information gain is the mean squared-error improvement (before minus after) for claims with assessments straddling their `VerificationResolved` tick. Documentation of every metric's derivation lives in `packages/benchmark/README.md` and the module's own doc-comments, satisfying "recomputable from verified artifacts" for any third party holding the same player-event-log JSON.
4. **`@null-city/mcp-server` (`packages/mcp-server`) is the third client on the same public contract, not a second implementation.** `createNullCityMcpServer` (`src/server.ts`) constructs exactly one `PlayerSession` via `@null-city/sdk` (never an in-process engine handle) and registers nine tools (`src/tools.ts`) against it: three read-only observers (`get_state`, `get_events`, `get_completed_summary`), three read-only inspectors (`list_claims`, `list_teams`, `list_routes`), and three writers (`submit_command`, `submit_assessment`, `advance_time`). Every tool carries explicit MCP `annotations` (`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`) and bounds its own payload (`src/limits.ts`: list/event responses capped, with `total`/`truncated` fields so a client always knows if it's seeing a partial view — never a silent drop). There is deliberately no truth resource or tool, at any point, active or completed run: unlike the benchmark runner, `mcp-server/src/` never even imports `@null-city/server` (it always connects to an already-running one via `NULLCITY_BASE_URL`), and `test/forbidden-imports.test.ts` additionally scans registered tool names for `truth`/`snapshot`/`internal`/`admin` substrings.
5. **`advance_time` distinguishes the two ticks that legitimately differ under the epistemic boundary, rather than conflating them.** The server's `advance` response carries both a top-level `tick` (the deterministic clock's raw absolute position — public, and the field `packages/server/src/transport.ts`'s reference client already keys scheduling off of) and `publicState.tick` (the player-*observed* tick, i.e. the tick of the last player event actually produced — which legitimately lags while a newsworthy event is still in flight, per `packages/epistemics/src/bridge.ts#projectPlayerState`). The tool returns `tick: outcome.publicState.tick` (matching `get_state`'s meaning of "tick" everywhere else in the adapter) and `clockAdvancedTo: outcome.tick` for bookkeeping — this was caught and fixed via `test/parity.test.ts` asserting `get_state().tick === advance_time().tick` against a live server, not by inspection.
6. **Parity is proven by driving one real, shared `PlayerSession` through both a direct SDK call and the equivalent MCP tool call, over a real MCP `Client`/`McpServer` pair.** `packages/mcp-server/test/parity.test.ts` connects a real `@modelcontextprotocol/sdk` `Client` to the adapter's `McpServer` via `InMemoryTransport` (exercising the actual JSON-RPC tool-call and zod input-validation machinery, not a mocked call), and asserts: `get_state`/`list_teams`/`list_routes` mirror `session.getState()` exactly; `submit_command`/`submit_assessment`/`advance_time` mutate the one real session such that an immediately-following direct SDK read observes exactly what the tool reported; out-of-range assessment inputs are rejected by schema validation before ever reaching the session; the documented tool set and its read/write annotations are exactly as specified; every list/event response honors its documented bound. `test/leak.test.ts` additionally drives a full golden-script run entirely through MCP tool calls and scans every response with `@null-city/epistemics`'s `detectPublicLeak` (dev-only dependency).
7. **The optional LLM example is deliberately excluded from every automated gate and fails immediately and legibly without credentials.** `packages/mcp-server/examples/llm-openai-policy.mjs` wires an OpenAI chat model up as the tool-caller over the exact same MCP surface `quickstart.mjs` (the non-LLM, CI-covered example) drives; it depends on neither a workspace package nor `pnpm verify` — it throws a clear, actionable error the instant `OPENAI_API_KEY` (or the non-workspace `openai` package) is missing, rather than hanging or silently no-op'ing, and is documented as intentionally out of scope for the deterministic core.
8. **`pnpm verify` gains three new, fast, credential-free gates** (`verify:sdk` runs the SDK's own `examples/quickstart.mjs`; `verify:benchmark` runs a fixed one-scenario/two-policy smoke slice with a shortened tick-step, failing on any hash-chain-verification miss; `verify:mcp` runs the MCP adapter's `examples/quickstart.mjs`, which discovers all nine tools and completes a full run using only MCP tool calls) appended after `verify:command-center`, so a regression in any M5 package fails `pnpm verify` without requiring an API key or a long LLM-driven run. `pnpm bench` (full default matrix) and `pnpm mcp:start` (stdio server against an already-running `@null-city/server`) are added as top-level convenience scripts, not verify gates.

## Consequences

- Three new workspace packages (`@null-city/sdk`, `@null-city/benchmark`, `@null-city/mcp-server`) join the dependency graph; none of them is a production dependency of `@null-city/simulation`, `@null-city/epistemics`, or `@null-city/server` — the dependency arrow only ever points from player-facing code toward the public transport, never the reverse.
- `@null-city/server` becomes a **dev**-only dependency of `@null-city/sdk` and `@null-city/benchmark` (each owns an ephemeral server process for its own tests/runs) but is forbidden even as a dev import inside `@null-city/mcp-server/src/`, since the MCP adapter always connects outward to an already-running server rather than owning one.
- A minor, deliberate naming asymmetry now exists in the public `advance` response (`tick` = clock position, `publicState.tick` = player-observed tick); the MCP adapter renames its own `tick`/`clockAdvancedTo` fields to avoid re-exposing that ambiguity to MCP clients, but the underlying SDK/REST contract is unchanged from M0–M4.
- Two lint-only fixes were needed in already-existing `packages/benchmark/src/policies/*.ts` files (unused `_context` constructor-style parameters), resolved with the same `void <param>;` convention already used elsewhere in the codebase (e.g. `packages/server/src/rpc.ts`) rather than a broader ESLint config change.

## Unverified / deferred

- The optional LLM example (`examples/llm-openai-policy.mjs`) has not been run against a live OpenAI account as part of this milestone's verification — only its credential/dependency-missing failure path was exercised. It is explicitly out of `pnpm verify`'s scope by design.
- `pnpm bench`'s full default matrix (all scenarios × seeds × policies) was not run end-to-end as part of milestone verification, only the fixed `verify:benchmark` smoke slice (one scenario, two policies, shortened tick-step) — the full matrix is a manual/CI-optional convenience command, not a gate.
- No browser/Command Center change was required or made for M5; "same scenario/seed playable by browser, baseline policy, and MCP client" is demonstrated by three independent runs against the same `black-river`/`49314` public contract (`verify:player-cli`/`pnpm demo` for the browser-equivalent CLI, `verify:benchmark` for the baseline policy, `verify:mcp` for the MCP client), not by a single shared session across all three in one process.
